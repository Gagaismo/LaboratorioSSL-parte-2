1. Enunciado

Dadas las reglas léxicas y sintácticas del subconjunto de instrucciones LMD (Lenguaje de Manipulación de Datos) del lenguaje SQL que utilizan los SGBD (Sistemas Gestores de Bases de Datos), construir un Parser (analizador sintáctico) codificado en Java, utilizando las herramientas de metacompilación JLex y Cup. JLex parte de las expresiones regulares de los componentes léxicos del lenguaje y obtiene un Scanner (analizador léxico) en Java, capaz de obtener los tokens y suministrárselos al parser. Cup parte de una GIC descripta en notación BNF, que especifica las reglas sintácticas del lenguaje, y obtiene un parser en Java capaz de detectar los errores sintácticos a partir de un archivo de texto que contiene líneas de instrucciones LMD de SQL.

Las reglas del lenguaje son las del material de la cátedra Sintaxis estándar ANSI básica del LMD SQL:

INSERT INTO tabla (columna1, columna2...) VALUES (valor1, valor2...) ;
INSERT INTO tabla VALUES (valor1, valor2...) ;
UPDATE tabla SET columna1 = valor1, columna2 = valor2... WHERE columnaN = valorN ;
DELETE FROM tabla WHERE columna1 = valor1 ;
SELECT * FROM tabla ;
SELECT columna1, columna2... FROM tabla ;
  • tabla, columna1, columna2 son identificadores; si contienen espacios se escriben entre comillas dobles.
  • valor1, valor2 son expresiones del mismo tipo que las columnas. Las cadenas van entre comillas simples.
  • Las expresiones usan los operadores + - * / < > <= >= = AND OR NOT y solo números enteros.
  • En el INSERT con lista de columnas, las cantidades de columnas y de valores deben ser iguales.

2. Marco teórico

2.1. Análisis léxico y sintáctico

El analizador léxico (scanner) lee el texto fuente carácter por carácter y lo agrupa en lexemas; a cada lexema le asigna una categoría o token (palabra reservada, identificador, constante, operador). Los componentes léxicos son lenguajes regulares (tipo 3 de Chomsky), por lo que se describen con expresiones regulares y se reconocen con un autómata finito. El analizador sintáctico (parser) recibe la secuencia de tokens y verifica que respete la estructura del lenguaje, descripta con una gramática independiente del contexto (GIC, tipo 2), cuyo reconocedor es un autómata de pila.

2.2. JLex

JLex es un generador de analizadores léxicos para Java (el equivalente a Lex de C). Su archivo de especificación tiene tres secciones separadas por %%: código de usuario (copiado al principio del archivo generado: package e import), directivas (opciones como %class, %cup, %char, %ignorecase, código propio entre %{ %} y definiciones de macros con expresiones regulares) y reglas léxicas: pares expresión regular { acción en Java }. JLex construye un AFN por cada regla, lo convierte en un único AFD y lo minimiza. Al analizar aplica dos criterios: gana la regla que reconoce el lexema más largo y, si hay empate, la que está escrita primero.

2.3. Cup y el análisis LALR(1)

Cup (Constructor of Useful Parsers) es el equivalente de Yacc para Java. A partir de una GIC escrita en BNF genera un analizador ascendente LALR(1): construye la colección de elementos LR(1), fusiona los estados que tienen el mismo núcleo (eso es lo que distingue LALR de LR canónico) y produce las tablas ACCIÓN e IR-A. El parser es un autómata de pila que, en cada paso, mira el estado del tope de la pila y el token de entrada (un símbolo de anticipación) y hace una de cuatro cosas: desplazar el token y pasar a un estado, reducir por una producción (saca de la pila tantos símbolos como tiene la parte derecha, apila el no terminal de la izquierda y ejecuta su acción semántica), aceptar o informar un error. El archivo de Cup tiene cinco partes: paquete e importaciones, código de usuario (parser code {: ... :}), declaración de terminales y no terminales, precedencias, y símbolo inicial con las producciones.

2.4. Integración

Cup genera dos clases: el parser y una clase de constantes con un número por cada terminal (con las opciones -parser Parser -symbols Simbolos se llaman Parser y Simbolos, como en los ejemplos de la cátedra). Con la directiva %cup, la clase que genera JLex implementa la interfaz java_cup.runtime.Scanner: cada vez que el parser pide un token llama a next_token(), que devuelve un objeto java_cup.runtime.Symbol con el número de terminal (el mismo de Simbolos), su valor (el lexema) y su posición.

2.5. Recuperación de errores

Cup reserva el terminal especial error. Cuando la tabla indica error, el parser llama a syntax_error(), desapila hasta encontrar un estado que pueda desplazar error, lo desplaza y descarta tokens de entrada hasta que puede seguir analizando normalmente. Con la producción sentencia ::= error PTOCOMA un error dentro de una sentencia hace descartar el resto de esa sentencia hasta su punto y coma, y el análisis continúa con la siguiente.

3.2. Decisiones de diseño

  • Palabras reservadas sin distinguir mayúsculas: SQL no distingue SELECT de select. Se usa la directiva %ignorecase de JLex en lugar de escribir [Ss][Ee][Ll]....
  • Palabras reservadas antes que IDENTIFICADOR: el lexema FROM lo reconocen las dos reglas con la misma longitud, y gana la primera. En cambio fromage es un identificador porque esa regla reconoce un lexema más largo.
  • <= y >= se reconocen como un solo token por la regla del lexema más largo. El operador <> no está entre los que pide el material, así que se lee como < seguido de > y el parser lo rechaza.
  • Constantes: solo enteros, como indica el material; 1.10 produce un error léxico en el punto. Las cadenas usan comillas simples y admiten la comilla duplicada '' dentro, como en SQL estándar.
  • Posiciones: con %char cada token lleva su desplazamiento desde el inicio del archivo (left = inicio, right = fin). Con eso se informa la línea y la columna de cada error y Cup propaga las posiciones a los no terminales.
  • Errores léxicos: la última regla (.) atrapa cualquier carácter que no forme parte de un token, se informa con su línea y columna y el scanner sigue con el carácter siguiente (no se corta el análisis). También se informan las cadenas e identificadores entre comillas que no se cierran antes del fin de línea.
  • Comentarios -- ... hasta el fin de línea, como en SQL, para poder documentar los archivos de prueba.

4.2. Decisiones de diseño

  • Varias sentencias por archivo: lista_sentencias es recursiva a izquierda (la forma que conviene en un parser ascendente, porque no hace crecer la pila) y cada sentencia termina en ;.
  • Condiciones separadas de las expresiones: condicion combina comparaciones con AND, OR y NOT; expresion es aritmética. Así WHERE sueldo o WHERE a + 1 son errores sintácticos (falta la comparación) y SET x = a > b también.
  • Ambigüedad resuelta con precedencias: las reglas expresion ::= expresion MAS expresion o condicion ::= condicion AND condicion son ambiguas; las declaraciones precedence le indican a Cup cómo resolver los conflictos desplazar/reducir (por ejemplo, en a + b * c se desplaza el * porque tiene mayor precedencia, y en a - b - c se reduce primero por la asociatividad a izquierda). Con eso Cup informa 0 conflictos.
  • Igual cantidad de columnas y valores: en el INSERT con lista de columnas, la producción columnas_valores ::= IDENTIFICADOR COMA columnas_valores COMA expresion anida cada columna con su valor, igual que la gramática de anbn. La restricción, que una gramática regular no podría expresar, queda dentro de la GIC: INSERT INTO t (a, b) VALUES (1); es un error sintáctico ("se esperaba ','").
  • WHERE opcional en SELECT, UPDATE y DELETE (clausula_where ::= WHERE condicion | λ). El material muestra el SELECT básico sin WHERE, pero la condición es parte del estándar y de los casos de prueba.
  • Recuperación de errores: sentencia ::= error PTOCOMA. Además se redefine error_sync_size() para que devuelva 1: con el valor por defecto (3), después de un error Cup necesita analizar bien tres tokens seguidos, y si la sentencia siguiente también tiene un error, las dos se fusionan y el segundo error no se informa.
  • Mensajes de error: se redefine syntax_error() para informar línea, columna, el token inesperado y los terminales que se esperaban. Esos terminales salen de la fila del estado del tope en la tabla ACCIÓN, pero como LALR fusiona estados, la fila puede tener terminales que en ese contexto no corresponden; por eso cada candidato se prueba sobre una copia de la pila (aplicando las reducciones hasta ver si se desplaza). unrecovered_syntax_error() se redefine para informar la sentencia que quedó sin cerrar al final del archivo, sin lanzar una excepción.
  • Acciones semánticas: al reducir cada sentencia se informa si es correcta (y de qué tipo) o incorrecta, junto con los errores léxicos y sintácticos que ocurrieron entre su primer token y su ;. Una sentencia sintácticamente válida que tuvo errores léxicos (el scanner descartó caracteres) se informa como incorrecta.

5. Integración del scanner y el parser: programa principal

El paquete sql tiene cinco clases: Lexico (generada por JLex), Parser y Simbolos (generadas por Cup), Analisis y Main. Main abre el archivo como flujo de caracteres (UTF-8), crea el scanner con ese flujo, crea el parser pasándole el scanner y llama a parse(), igual que el Main del ejemplo lenC0 de la cátedra. Analisis es el estado compartido entre el scanner y el parser: guarda la posición de cada token y los errores pendientes, los asigna a la sentencia en la que ocurrieron, traduce las posiciones a línea y columna y escribe el informe y el resumen. El programa termina con código 0 si no hubo errores y 1 si los hubo.

6. Compilación y ejecución

El script construir.bat hace los pasos que muestran los videos de la cátedra, desde la línea de comandos (requiere un JDK 8 o posterior):

javac -d build\herramientas herramientas\JLex\Main.java herramientas\java_cup\*.java herramientas\java_cup\runtime\*.java
cd src\sql
java -cp ..\..\build\herramientas JLex.Main Sql.lex          (genera Sql.lex.java, se renombra a Lexico.java)
java -cp ..\..\build\herramientas java_cup.Main -parser Parser -symbols Simbolos < Sql.cup
cd ..\..
javac -cp build\herramientas -d build\clases src\sql\*.java
java -cp build\clases;build\herramientas sql.Main pruebas\validas.sql

Para NetBeans: crear un proyecto Java con fuentes existentes, agregar src (paquete sql) y herramientas (paquete java_cup.runtime) como carpetas de fuentes y pasar la ruta del archivo .sql como argumento en Run → Set Project Configuration → Arguments. Las clases generadas (Lexico, Parser, Simbolos) están incluidas en el repositorio, así que no hace falta volver a generarlas para ejecutar.

8. Interfaces web y de consola

Para usar el analizador sin instalar Java se publicaron dos interfaces en GitHub Pages. No reimplementan la gramática: el scanner reproduce las mismas reglas de Sql.lex (lexema más largo, y a igual longitud la primera regla), y el parser ejecuta las tablas que generó Cup, exportadas desde Parser.java por herramientas/exportar/ExportarTablas.java, con el mismo algoritmo de java_cup.runtime.lr_parser, incluida la recuperación de errores.

  • Interfaz gráfica (index.html): editor del archivo de entrada (o apertura de un .sql), informe por sentencia con los errores marcados sobre el texto, árbol de análisis sintáctico de cada sentencia, tabla de tokens, traza del parser, especificación (expresiones regulares y GIC) y tabla LALR(1) completa.
  • Consola (consola.html), al estilo de una TUI: se escriben sentencias (pueden ocupar varias líneas hasta el ;) o comandos: ejemplo, archivo, tokens on|off, arbol on|off, traza on|off, gramatica, lexico, producciones, estado <n>, con historial y atajos de teclado.

9. Conclusiones

JLex y Cup separan el problema en las dos capas de la jerarquía de Chomsky que corresponden: los componentes léxicos, regulares, se describen con expresiones regulares y se reconocen con el AFD que genera JLex; la estructura de las sentencias, independiente del contexto, se describe con una GIC y se reconoce con el autómata de pila LALR(1) que genera Cup. A partir de las especificaciones (Sql.lex de {{LINEAS_LEX}} líneas y Sql.cup de {{LINEAS_CUP}}) las herramientas generaron {{LINEAS_GENERADAS}} líneas de Java, con tablas de {{CANTIDAD_ESTADOS}} estados. Las restricciones que parecen "de contexto", como la igualdad entre la cantidad de columnas y de valores, se pudieron expresar en la GIC porque tienen la forma anbn. La parte que más trabajo llevó fue el tratamiento de errores: ubicar cada error en su sentencia, sincronizar después de un error y dar mensajes que indiquen qué se esperaba.
